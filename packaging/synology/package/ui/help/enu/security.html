Security posture

The Security page configures package policy within fixed fail-closed boundaries. Permissions & risk is the first tab. Observability & limits is the second and groups bounded request/result resources with structured log-category levels. A saved posture may narrow behavior or require stronger evidence; it cannot turn the native AppWindow into a public endpoint, return secrets, remove DSM authentication, or grant root execution.

Identity and request protections

  • The SPK runs as its DSM package identity and joins only the reviewed internal web-service group.
  • The AppWindow uses the current same-origin DSM session cookie; it does not accept launch tokens from URLs, fragments, history, or local storage.
  • Mutations require authenticated POST, a package CSRF token, a fixed request marker, a strict action schema, and bounded bodies.
  • The control socket remains package-private and requests are handled by the package-owned service.

Configurable policy

The dashboard always submits one complete policy document. Invalid, incomplete, duplicate, or unsupported values are rejected rather than silently weakened.

Require HTTPS
Rejects dashboard requests unless DSM reports an HTTPS connection.
Interface changes
Allows audited browser theme and refresh-cadence persistence.
Profile and secret changes
Separately controls ordinary profile fields and write-only password, TOTP, or collector-token operations.
Routine changes
Controls interval, daily-window, realtime, dependency, retry, and routine-deletion policy.
Notification changes
Controls package alert policy and audited open-session notification preferences.
Operational actions
Controls manual plan, run, and Target Doctor requests.

Risk ceilings

HTTP targets
When off, a profile cannot enable unencrypted HTTP.
Empty source
When off, a profile cannot disable the empty-source deletion guard.
Invalid TLS
When off, a profile cannot bypass destination certificate validation.
Destructive sync
When off, profiles, routines, and operations cannot enable destination deletion.
Doctor write test
When off, Target Doctor remains read-only even if the package reports write-test capability.
Remote logging
When off, profiles cannot configure an HTTPS collector or change its write-only token.

Request and result bounds

CSRF lifetime
60 through 900 seconds for a session-bound mutation token.
Result retention
300 through 86400 seconds for completed queued results.
Maximum outstanding jobs
N is 1 through 256 and caps queued plus processing jobs. Retained terminal responses are capped separately at the same N, so the worst case is 2N private job records.

Secrets

Protected values are accepted only through dedicated write operations. Status reports presence flags, never values. Navigating away, hiding DSM, closing an editor, or destroying the AppWindow clears browser-held secret fields. Avoid copying secrets into profile names, paths, URLs, alerts, or logs.

Deletion defense

Remote deletion requires explicit agreement across each applicable layer: profile policy, manual operation or routine policy, and numeric ceilings. Empty-source protection remains independent. A configurable policy should strengthen these gates, not bypass them.

Audit and log categories

Each of audit, bridge, authentication, security, configuration, secrets, routines, operations, notifications, sync, controller, and scheduler accepts off, trace, debug, info, warn, or error. Enable only the detail needed for operations and incident response. Mandatory minimal action audit records remain at info even when optional audit verbosity is off. Sensitive request bodies and credential material remain excluded regardless of category selection.

Applying changes

Policy changes take effect only after validation and an authenticated save. If the queued result cannot be observed, treat the outcome as unknown, inspect Activity and logs, and avoid blindly resubmitting the same change.
