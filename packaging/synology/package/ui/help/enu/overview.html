Synology Drive Sync

Synology Drive Sync copies files in one direction from a local NAS folder to a configurable Synology File Station destination. The native AppWindow lets DSM administrators configure profiles, plan or run work, schedule routines, inspect health evidence, and review bounded logs.

Start safely

  1. Create a profile and store its destination credentials.
  2. Open Health / Doctor and verify the source, File Station route, authentication, and destination.
  3. Run a plan before the first real sync.
  4. Run a sync with deletion disabled, inspect Activity, and only then consider a bounded deletion policy.
  5. Add an automation routine after manual acceptance succeeds.

Overview indicators

Profiles
Configured destinations and whether protected password material is present.
Next routine
The earliest controller-reported execution time among enabled routines.
Last result
The package's verdict on the latest run (Succeeded, Partial, Failed, Cancelled, Busy, Stale or Not run), its completion time, and the cause when one is known. A value this window does not recognise is shown as unknown (value), never hidden.
Active scope
The profile or all-profile scope currently using the host-local operation lock.
Realtime
Enabled realtime routines, and whether any of them are watching natively, using the polling floor, or not currently observing changes at all.

Run outcomes and attention

Nothing that goes wrong is left silent. A list above the indicators names every run failure, partial run, stale run, alert problem and degraded package record, each with its cause and the next step. For example, Scheduled runs can't start: package paths mismatch means the profile's log file is not the package-managed path; repair the package or reset that setting. The list is empty only when the package reports nothing wrong.

Partial
The run finished (exit code 3) but deferred or skipped some files, for example because they changed during the run. The count and cause are named, and they are left for the next run. A partial run is a warning, never success, and only means transient deferrals. A run that changed the destination and then failed is a failure, not partial.
Stale
A run was recorded as running but its runner is gone (killed, out of memory, power loss). Its real result is unknown and counts as a failure.
Succeeded with warnings
The run exited cleanly but left entries out that will not sync until fixed: skipped entries (names the destination cannot hold, links, case collisions) or lasting deferrals. The count is shown, the entries are listed as entry.skipped and entry.deferred records in the sync log with path and reason, and the run is never shown as plain success.
Result warnings
A run can carry extra facts, each shown as a warning with its count: folders whose listing came back incomplete (deletions there were held back; up to five are named, and the destination root is named as such), uploads whose modification time the NAS did not keep (they upload again on the next run; run Doctor's write probe), re-login failures, server-side tasks that could not be stopped on the target, and keep-alive failures the run recovered from.
Busy and Cancelled
Busy means another run, Doctor or management action held the run lock and the run is retried. Cancelled means it was stopped. Neither is shown as success.
Failed N times in a row
The consecutive failed sync count the failure alert uses. Failure alerts unavailable means the alert state file is unreadable, so failure notifications are disabled until the package is repaired.
Some records of this run could not be written
The run's own result is trustworthy, but an echo of it (the Activity line, the alert counter or the DSM log) was not written. The affected records are named.
Routine deferred
A routine did not start because of a dependency, a source condition or a deletion bound, or its last execution exited with an error. Waiting for a daily window or for the run lock is expected and is not listed. Routine ... is blocked is different: the routine's own deletion limit is lower than its profile's max-delete, so the controller refuses every run before it starts and it can never run until one of the two limits is changed on the Routines page.
Running for a long time
A run that has been going for more than six hours is listed with its age and a prompt to check whether it is stuck. A core waiting on an unresponsive source or target never fails, it just never finishes, and every routine waits behind it (shown as Waiting (busy), not as healthy).
No progress for 30 minutes
A running sync whose heartbeat has stopped advancing is listed as possibly stuck.
Core error output
When the last run failed, the failing profile also shows the core's own error line and the path it failed on, once the runner records them. When the last run failed, the package keeps the core's own error text. It is shown under the list as Core error output of the last run (or the reason it could not be read), and the same text is available under Activity, Package logs, source Core error output.
Stored status figures are degraded
The stored sync totals could not be read; the cause is shown beside Oldest evidence in the Sync summary.
Last run failed, N failures in a row
Stays on screen, from the package's own records, until a successful run clears it. An all-profiles failure also stays listed after a later single-profile run overwrites the latest result.
Package record-keeping is degraded
Some of the package's own state files could not be read; the results shown may be incomplete.

Each profile on this page also shows its own last run: outcome, cause, how long ago, and how many failures in a row. A profile without a routine is never reported as healthy only because Doctor passed. When a failure is present as this window loads, it is announced once, even if it happened while no window was open, and the list stays until the cause is gone. A package that reports no outcomes at all, or reports them in a shape this window cannot read (another schema version, no run record, an outcome that is not text), is shown as Run outcomes unavailable with Status unavailable: and the reason, not as healthy. A reason code this window has no text for is shown as unknown reason (code) with its raw code and is never given a neutral colour. When the package says a run died (Stale), the Overview, the profile rows and the desktop card say so and stop showing a run as active, even though the older run record still reads running. A routine that is only waiting for its daily window, or for another run to finish, is not flagged on the desktop card. A save that succeeded but could not take full effect (for example the running controller could not be told to reload the new schedule) shows Saved, but it is not fully in effect with every cause the package reported until you dismiss it or a later save succeeds. While a saved change is still waiting for the running controller to pick it up, the list also shows Saved, not yet applied; restart the package service, which stays until the controller has reloaded. Ages such as 5 min ago are counted on the package's clock and keep advancing between refreshes.

Package bridge status

Authenticated package bridge means the same-origin DSM session passed package authentication and the AppWindow holds a current CSRF token. Package status - read-only means status is visible but mutation capabilities are not granted. Package-generated GET failures use HTTP transport 200 so Webman preserves the body; the banner still treats ok=false as failure and reports the original semantic status, code, and stage. A raw empty or HTML 4xx/5xx response instead points to Webman, proxy, route, or CGI-launch handling. The last successful snapshot remains visible as stale evidence, dimmed, with its age shown, and none of its rows is shown as succeeded or healthy while the package is not answering; use Retry after completing the banner's recovery instruction. Every failure ends with a Detail line giving the HTTP status, the package's own error code and, when the package sent one, its message, so a package that answered with an error is not described as unreachable. After the second failed read in a row the window retries more and more slowly, and a minimised window reads no faster than the desktop card. If the dashboard itself fails while drawing, a banner reading The dashboard hit an internal error appears at the top of the window with a Reload this window button; the numbers below it may be out of date until you reload.

Safety defaults

  • Sync direction is local source to remote File Station destination.
  • Deletion is disabled unless independently approved by profile, operation, and routine policy.
  • Secret values are write-only and are never returned to the browser.
  • Manual work and routines share one host-local lock so sync operations cannot overlap.
  • Closing the AppWindow stops browser observation; it does not cancel a job already accepted by the package.
