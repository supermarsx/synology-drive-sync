Routines and realtime hooks

The page opens on Configured profiles, where each saved routine can be inspected and selected. Selecting one switches to Package controller, the editor for that profile's automation policy. Each profile can have one package-controller routine. A routine remains inert until it is saved and enabled. Choose Sync for a real transfer or Plan only for read-only comparison.

Execution modes

Interval
Runs after the configured number of seconds, subject to enabled weekdays and the operation lock.
Daily window
Runs only between the start and end times in DSM local time.
Realtime
Observes source changes, waits for the debounce period, performs preflight, and starts a run. When a native change hook is unavailable, the package reports and uses the configured polling fallback.

Timing model

Realtime work follows four stages: observe, debounce, preflight, run. Debounce coalesces bursts of changes. Fallback poll controls how often the source is checked without native hooks. Retry attempts and backoff apply after an execution fails; they do not permit overlapping operations.

Dependencies and weekdays

Wait-for dependencies require selected profile routines to finish first. Avoid dependency cycles. At least one active weekday is required. The controller evaluates daily-window times and weekdays using the NAS clock, so keep DSM time synchronization healthy.

Deletion policy

A routine cannot independently enable deletion. It can only permit deletion already allowed by the profile, and its deletion approval ceiling adds another limit. Use a plan to review proposed removals before enabling either layer.

One host-local lock

Manual plans, manual syncs, Doctor operations, and scheduled routines coordinate through package state. A long-running sync cannot pile up concurrent sync processes; subsequent routine work waits or records the controller decision.

Removing a routine

Removing a routine stops package automation for the profile. The profile, credentials, and synchronized files remain intact.
